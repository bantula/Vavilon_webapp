ROOT CAUSE IDENTIFIED
═══════════════════════════════════════════════════════════════════

Problem: "First sentence works, then recognition stops permanently"

Analysis:
- Standalone Python script with TranslationRecognizer works continuously (multiple sentences) ✓
- Online WebSocket version translates first sentence correctly ✓
- After first translated sentence, recognition stops permanently ✗
- English → English bypass mode works continuously ✓
- Translation itself works (first sentence proves Azure credentials and SDK are functional) ✓

Conclusion:
This is a RECOGNIZER LIFECYCLE issue in the server WebSocket pipeline, not a translation configuration problem.

Most Likely Cause:
- The Azure SDK's `session_stopped` event is firing prematurely after the first successful recognition
- This could be triggered by:
  * Audio stream being closed inadvertently
  * SDK internal timeout (though unlikely with continuous recognition)
  * Race condition in callback handlers
  * Stream buffer underrun or error

Current Implementation (CORRECT but lacking visibility):
✓ Uses TranslationRecognizer (not SpeechRecognizer)
✓ Uses start_continuous_recognition_async() (not recognize_once_async)
✓ Recognizer stored in session object (not recreated per chunk)
✓ Audio stream NOT closed in recognized callback
✓ stop_continuous_recognition() only called in session.stop()

Gap:
✗ No logging to detect WHEN session_stopped fires
✗ No state tracking to identify unexpected lifecycle transitions
✗ No visibility into whether stop is premature or intentional

HOW LIFECYCLE NOW WORKS (With Enhanced Monitoring)
═══════════════════════════════════════════════════════════════════

Phase 1: Session Initialization
────────────────────────────────
Frontend: Speaker clicks "Start Speaking"
  ↓
Backend: POST /start-session
  ↓
AI Service: TranslationSession.__init__()
  - Create PushAudioInputStream (stream stays open)
  - Create TranslationRecognizer (recognizer persists)
  - Attach callbacks (session_started, recognized, session_stopped, etc.)
  - Log: "recognizer_created"
  ↓
AI Service: session.start()
  - Log: "starting_recognition" (mode='continuous')
  - Call: start_continuous_recognition_async().get()
  - Set: _recognition_started = True
  - Log: "recognition_started" (lifecycle_state='active')
  ↓
SDK Callback: _on_session_started()
  - Log: "azure_session_started" (recognition_active=True)
  - Note: "Azure SDK session started - recognition pipeline active"

Phase 2: Continuous Audio Streaming
────────────────────────────────────
Loop (until speaker disconnects):
  
  Frontend: Capture audio chunk
    ↓
  Backend: Receive via WebSocket, forward via HTTP
    ↓
  AI Service: POST /process-audio → session.push_audio(bytes)
    - Check: Stream not closed (_stream_closed == False)
    - Write: audio_stream.write(bytes)
    - Every 50th chunk: Log with recognition_active and stream_open states
    ↓
  SDK: Continuous recognition processes audio
    ↓
  SDK Callback: _on_recognizing() [partial results]
    - Log first 3 partials to confirm audio reaching Azure
    ↓
  SDK Callback: _on_recognized() [final result]
    - Extract: source_text = evt.result.text
    - Extract: translations = evt.result.translations
    - Log: "stt_recognized" with recognize_no (1, 2, 3, ...)
    - For each target language:
      * Get translated text from translations dict
      * Log: "translated" (language, text)
      * Queue for TTS
      * Broadcast subtitle
    - ⚠️ DOES NOT call stop_continuous_recognition()
    - ⚠️ DOES NOT close audio_stream
    - Recognition continues...
    ↓
  Next audio chunk arrives → Repeat

  This loop continues indefinitely, processing multiple sentences.

Phase 3: Premature Stop Detection (NEW)
────────────────────────────────────────
IF Azure SDK fires session_stopped event:
  
  SDK Callback: _on_session_stopped()
    - Calculate: was_unexpected = (
        recognize_count > 0 AND           # At least one sentence processed
        NOT stop_called AND               # stop() was NOT called by us
        NOT recognition_stopped           # Recognition not already stopped
      )
    
    IF was_unexpected:
      - Log level: 'warn'
      - Log: "azure_session_stopped" with unexpected=True
      - Note: "UNEXPECTED session stop - recognition should be continuous"
      - This reveals the bug: SDK stopped on its own!
      - Includes recognition_count to show how many succeeded before stop
    
    ELSE:
      - Log level: 'info'
      - Log: "azure_session_stopped" with unexpected=False
      - Note: "Normal session_stopped after explicit stop()"

Phase 4: Normal Session Termination
────────────────────────────────────
Frontend: Speaker clicks "Stop" or closes page
  ↓
Backend: POST /end-session
  ↓
AI Service: session.stop()
  - Log: "stopping" (lifecycle_state='stopping', note="Explicit stop() called")
  - Set: _stop_event
  - Stop TTS threads
  - Log: "stopping_recognition"
  - Call: stop_continuous_recognition_async().get()
  - Set: _recognition_stopped = True
  - Log: "recognition_stopped"
  - Log: "closing_audio_stream"
  - Call: audio_stream.close()
  - Set: _stream_closed = True
  - Log: "audio_stream_closed"
  - Join TTS threads
  - Log: "stopped" (lifecycle_state='stopped')
  ↓
SDK Callback: _on_session_stopped()
  - Calculate: was_unexpected = False (stop was called)
  - Log: "azure_session_stopped" with unexpected=False
  - Note: "Normal session_stopped after explicit stop()"

If you see "unexpected":true in azure_session_stopped:
- Root cause: Azure SDK session is terminating prematurely
- Possible reasons:
  1. Audio stream buffer underrun
  2. SDK internal timeout (check Speech_SegmentationSilenceTimeoutMs)
  3. Stream format mismatch
  4. SDK version bug
  5. Network issue with Azure endpoint
- Next steps:
  1. Check if audio is still being pushed (look for "audio_pushed" logs)
  2. Check if any "canceled" events fire (would indicate SDK error)
  3. Check Azure SDK version compatibility
  4. Try increasing Speech_SegmentationSilenceTimeoutMs
  5. Consider REST API fallback for STT (not just TTS)
